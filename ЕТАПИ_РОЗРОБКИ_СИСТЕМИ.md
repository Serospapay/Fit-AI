## Етап 1. Підготовка та налаштування проєкту

На початку створюється базова структура проєкту: frontend і backend у монорепозиторії, підключаються залежності, налаштовуються змінні середовища та скрипти запуску.

### Конфігурація через .env

Токени, URL бази даних та інші налаштування зберігаються у файлі .env, щоб не залишати секрети в коді.

```typescript
// backend/src/lib/config.ts
import dotenv from 'dotenv';
dotenv.config();

const nodeEnv = process.env.NODE_ENV || 'development';
const isProduction = nodeEnv === 'production';

for (const key of ['DATABASE_URL'] as const) {
  if (!process.env[key]?.trim()) throw new Error(`Missing required env: ${key}`);
}
if (isProduction && (!process.env.JWT_SECRET || process.env.JWT_SECRET.length < 16)) {
  throw new Error('JWT_SECRET is required in production (min 16 chars)');
}

export const config = {
  NODE_ENV: nodeEnv,
  PORT: parseInt(process.env.PORT || '5000', 10),
  DATABASE_URL: process.env.DATABASE_URL!,
  JWT_SECRET: process.env.JWT_SECRET || (isProduction ? '' : 'dev-secret-only-for-local'),
  JWT_EXPIRES_IN: process.env.JWT_EXPIRES_IN || '7d',
  CORS_ORIGIN: process.env.CORS_ORIGIN || 'http://localhost:3000',
};
```

**Пояснення:** dotenv завантажує змінні з .env. У production обов'язково перевіряється JWT_SECRET — без нього сервер не запуститься. У development використовується dev-secret для спрощення локальної розробки.

### Скрипти запуску та міграції

У package.json визначені скрипти для розробки, збірки, міграцій БД та seed-даних.

```json

    "build": "tsc",
    "start": "node dist/index.js",
    "prisma:generate": "prisma generate",
    "prisma:migrate": "prisma migrate dev",
    "prisma:seed": "ts-node prisma/seed.ts",
    "prisma:seed:user": "ts-node prisma/seed-user.ts",

```

**Пояснення:** nodemon перезапускає сервер при зміні файлів. Окремі скрипти для seed базових довідників (exercises, foods, quotes), тестового користувача та повного демо-контенту дозволяють гнучко наповнювати БД.

### Точка входу та graceful shutdown

Головний файл index.ts запускає HTTP-сервер, підключає Prisma і обробляє сигнали завершення для коректного закриття з'єднань.

```typescript
// backend/src/index.ts
import app from './app';
import logger from './lib/logger';
import { config } from './lib/config';
import { prisma } from './lib/prisma';

const PORT = config.PORT;

const server = app.listen(PORT, () => {
  logger.info(`Server running on http://localhost:${PORT}`);
  logger.info(`Health check: http://localhost:${PORT}/api/health`);
});

const gracefulShutdown = async (signal: string) => {
  logger.info(`Received ${signal}. Starting graceful shutdown...`);

  server.close(async () => {
    try {
      await prisma.$disconnect();
      logger.info('Database disconnected');
    } catch (err) {
      logger.error('Error disconnecting database:', err);
    }
    logger.info('HTTP server closed');
    process.exit(0);
  });

  setTimeout(() => {
    logger.error('Forced shutdown after timeout');
    process.exit(1);
  }, 10000);
};

process.on('SIGTERM', () => gracefulShutdown('SIGTERM'));
process.on('SIGINT', () => gracefulShutdown('SIGINT'));
```

**Пояснення:** При SIGTERM або SIGINT (Ctrl+C) сервер перестає приймати нові запити, закриває з'єднання з PostgreSQL і завершує процес. Таймаут 10 секунд запобігає зависанню, якщо disconnect не вдається.

## Етап 2. Проєктування архітектури системи

Після стартової конфігурації фіксується архітектура: Next.js як UI-шар, Express як API-шар, PostgreSQL як джерело даних. Роутери розділені за доменами.

**Пояснення:** notFoundHandler обробляє невідомі шляхи, errorHandler — всі помилки контролерів. Централізована обробка дає однакову структуру відповіді на помилки по всьому API.

### Health-check та логування запитів

Перед роутерами підключаються middleware для безпеки, лімітів, CORS і логування кожного запиту.

```typescript
app.use(helmet({ contentSecurityPolicy: false }));

app.use(rateLimit({
  windowMs: 15 * 60 * 1000,
  max: 200,
  message: { error: 'Too many requests', message: 'Спробуйте пізніше' },

    ip: req.ip,

    status: 'ok',
```

**Пояснення:** helmet додає безпечні HTTP-заголовки. rateLimit обмежує 200 запитів на 15 хвилин з однієї IP. CORS у production дозволяє лише вказаний origin. Health-check потрібен для перевірки доступності API з frontend або зовнішніх моніторингів.

## Етап 3. Проєктування та створення бази даних

Третім кроком було створення бази даних для зберігання користувачів, тренувань, харчування, цілей, нагадувань, рекомендацій та довідників.

### Основні сутності

Prisma schema описує всі моделі та зв'язки. Користувач — центральна сутність, до неї прив'язані тренування, щоденник харчування, цілі, нагадування, рекомендації та шаблони тренувань.

```prisma
// backend/prisma/schema.prisma (фрагмент)
model User {
  id            String    @id @default(cuid())
  email         String    @unique
  passwordHash  String
  name          String?
  // ... age, gender, height, weight, activityLevel, goal
  workouts      Workout[]
  nutritionLogs NutritionLog[]
  goals         Goal[]
  // ...
}

model Workout {
  id        String    @id @default(cuid())
  userId    String
  date      DateTime  @default(now())
  type      String?
  duration  Int?
  notes     String?
  rating    Int?
  user      User      @relation(fields: [userId], references: [id], onDelete: Cascade)
  exercises WorkoutExercise[]
  @@index([userId, date])
}

model WorkoutExercise {
  id          String   @id @default(cuid())
  workoutId   String
  exerciseId  String
  sets        Int?
  reps        Int?
  weight      Float?
  order       Int      @default(0)
  workout     Workout  @relation(fields: [workoutId], references: [id], onDelete: Cascade)
  exercise    Exercise @relation(fields: [exerciseId], references: [id])
}
```

**Пояснення:** onDelete: Cascade означає, що при видаленні користувача автоматично видаляються всі його тренування, записи харчування, цілі тощо. Індекси на userId та date прискорюють запити за користувачем і діапазоном дат.

### Щоденник харчування та довідники

NutritionLog — це прийом їжі (сніданок, обід, вечеря, перекус). Кожен запис містить список NutritionItem з продуктами, кількістю та калоріями. Food — довідник продуктів для автодоповнення.

```prisma
model NutritionLog {
  id        String    @id @default(cuid())

model NutritionItem {
  id             String    @id @default(cuid())

  calories       Float

  fat            Float  @default(0)

model Food {
  id       String   @id @default(cuid())

  calories Float
  protein  Float  @default(0)

```

**Пояснення:** mealType дозволяє фільтрувати прийоми їжі. NutritionItem зберігає БЖУ на порцію. Food — глобальний довідник, який заповнюється seed-скриптом і використовується для пошуку при додаванні їжі.

## Етап 4. Реалізація базового backend-каркасу

На цьому етапі піднімається сервер із middleware безпеки, окремими rate-limit для auth, Swagger-документацією та централізованою обробкою помилок.

### Окремий rate-limit для логіну та реєстрації

Щоб захиститися від підбору паролів, на /api/auth/login та /api/auth/register встановлено жорсткіший ліміт — 100 спроб за 15 хвилин.

```typescript
const authLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  max: 100,
  message: { error: 'Too many attempts', message: 'Забагато спроб входу. Спробуйте через 15 хвилин.' },
});
app.use('/api/auth/login', authLimiter);
app.use('/api/auth/register', authLimiter);
```

**Пояснення:** Глобальний rateLimit (200/15хв) застосовується до всього API. authLimiter додатково обмежує саме ендпоінти авторизації, оскільки вони найбільш вразливі до brute-force.

### Централізований error handler

Усі помилки з контролерів потрапляють у errorHandler. Він логує стек, формує зрозуміле повідомлення для клієнта і повертає відповідний HTTP-код.

```typescript
// middleware/errorHandler.ts — приклад використання
export const handleControllerError = (
  res: Response,
  error: unknown,
  opts: { controller: string; operation: string; errorTitle: string; userMessage: string; details?: object }
) => {
  logger.error(`${opts.controller}.${opts.operation}`, {
    error: error instanceof Error ? error.message : String(error),
    stack: error instanceof Error ? error.stack : undefined,
    ...opts.details,
  });
  const statusCode = error instanceof PrismaClientKnownRequestError ? 400 : 500;
  return res.status(statusCode).json({
    error: opts.errorTitle,
    message: opts.userMessage,
  });
};

// У контролері:
} catch (error: unknown) {
  return handleControllerError(res, error, {
    controller: 'WorkoutController',
    operation: 'createWorkout',
    errorTitle: 'Помилка створення тренування',
    userMessage: 'Не вдалося створити тренування.',
  });
}
```

**Пояснення:** handleControllerError уніфікує логування та відповідь. Користувач отримує коротке повідомлення, а в логах зберігається повний контекст для діагностики.

## Етап 5. Реалізація авторизації та доступу

Додаються реєстрація, логін, хешування пароля через bcrypt, JWT для stateless-авторизації та middleware authenticateToken для захисту приватних ендпоінтів.

### Хешування пароля та генерація токена

Пароль ніколи не зберігається в відкритому вигляді. JWT містить лише userId і термін дії. Сервер не тримає сесій — клієнт передає токен у заголовку Authorization.

```typescript
// backend/src/utils/auth.ts
import * as bcrypt from 'bcrypt';
import * as jwt from 'jsonwebtoken';

export const hashPassword = async (p: string) => bcrypt.hash(p, 10);
export const comparePassword = async (p: string, h: string) => bcrypt.compare(p, h);
export const generateToken = (userId: string) =>
  jwt.sign({ userId }, config.JWT_SECRET, { expiresIn: config.JWT_EXPIRES_IN });

export const verifyToken = (token: string): { userId: string } | null => {
  try {
    const decoded = jwt.verify(token, config.JWT_SECRET);
    return typeof decoded === 'object' && decoded !== null && 'userId' in decoded
      ? decoded as { userId: string } : null;
  } catch { return null; }
};
```

**Пояснення:** bcrypt з коефіцієнтом 10 дає достатньо стійке хешування. verifyToken повертає null при простроченому або невалідному токені — тоді middleware поверне 401.

### Middleware authenticateToken

Кожен захищений маршрут перевіряє наявність заголовка Authorization: Bearer <token> і валідність токена.

```typescript
// backend/src/middleware/auth.ts
import { Response, NextFunction } from 'express';
import { AuthRequest } from '../types';
import { verifyToken } from '../utils/auth';

export const authenticateToken = (req: AuthRequest, res: Response, next: NextFunction) => {
  const authHeader = req.headers.authorization;
  const token = authHeader?.startsWith('Bearer ') ? authHeader.slice(7) : null;

  if (!token) {
    return res.status(401).json({ error: 'Unauthorized', message: 'Token is required' });
  }

  const decoded = verifyToken(token);
  if (!decoded) {
    return res.status(401).json({ error: 'Unauthorized', message: 'Invalid or expired token' });
  }

  req.userId = decoded.userId;
  next();
};
```

**Пояснення:** req.userId заповнюється лише після успішної перевірки. Контролери отримують userId з req.userId і фільтрують дані тільки по цьому користувачу.

### Валідація вхідних даних через Zod

Перед обробкою логіну та реєстрації вхідні дані валідуються. Email нормалізується (trim, toLowerCase), щоб уникнути помилок через пробіли або різний регістр.

```typescript
// backend/src/validation/auth.schema.ts
import { z } from 'zod';

const emailSchema = z.string()
  .trim()
  .toLowerCase()
  .refine((val) => /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(val), {
    message: 'Невірний формат email',
  });

export const loginSchema = z.object({
  email: emailSchema,
  password: z.string().min(1, 'Пароль обовʼязковий'),
});

export const registerSchema = z.object({
  email: emailSchema,
  password: z.string().min(6, 'Пароль має містити мінімум 6 символів'),
  name: z.string().trim().max(120).optional().nullable(),
});
```

**Пояснення:** trim і toLowerCase гарантують, що " Demo@Example.com " і "demo@example.com" будуть однаковими. Без цього користувач міг би не ввійти після реєстрації через різний регістр.

### Логін з auto-створенням demo-користувача

У development, якщо користувач вводить demo@example.com, а такого запису немає, він автоматично створюється з паролем demo123. Це спрощує демонстрацію без ручного seed.

```typescript
// backend/src/controllers/auth.controller.ts (фрагмент)
const normalizedEmail = email.trim().toLowerCase();
let user = await prisma.user.findUnique({ where: { email: normalizedEmail } });

if (!user && config.NODE_ENV !== 'production' && normalizedEmail === 'demo@example.com') {
  user = await prisma.user.create({
    data: { email: normalizedEmail, passwordHash: await hashPassword('demo123'), name: 'Тестовий користувач' },
  });
}
if (!user) return res.status(401).json({ error: 'Invalid email or password' });
if (!(await comparePassword(password, user.passwordHash))) return res.status(401).json({ error: 'Invalid email or password' });

res.json({ user: { id: user.id, email: user.email, name: user.name }, token: generateToken(user.id) });
```

**Пояснення:** У production auto-створення вимкнено. У development демо-логін завжди доступний, навіть якщо seed не виконували.

## Етап 6. Реалізація ключового бізнес-функціоналу backend

Розробляються CRUD-сценарії для тренувань, харчування, цілей, нагадувань, рекомендацій. Для тренувань додано складну статистику: агрегація за період, серія днів, досягнення, графіки.

### Створення тренування з вправами

Тренування створюється разом зі списком вправ. Кожна вправа має exerciseId (з довідника), sets, reps, weight, duration, distance, rest, order.

```typescript
// backend/src/controllers/workout.controller.ts (фрагмент)
export const createWorkout = async (req: AuthRequest, res: Response) => {
  const userId = req.userId!;
  const { date, time, type, duration, notes, rating, exercises } = req.body;

  let workoutDate = date ? new Date(date) : new Date();
  if (time) {
    const [h, m] = time.split(':');
    workoutDate.setHours(parseInt(h) || 0, parseInt(m) || 0, 0, 0);
  }

  const workout = await prisma.workout.create({
    data: {
      userId,
      date: workoutDate,
      type: type || null,
      duration: duration || null,
      notes: notes || null,
      rating: rating || null,
      exercises: {
        create: exercises?.map((ex: any, i: number) => ({
          exerciseId: ex.exerciseId,
          sets: ex.sets, reps: ex.reps, weight: ex.weight,
          duration: ex.duration, distance: ex.distance, rest: ex.rest,
          order: ex.order ?? i, notes: ex.notes
        })) || []
      }
    },
    include: { exercises: { include: { exercise: true } } }
  });

  res.status(201).json(workout);
};
```

**Пояснення:** Вкладені create дозволяють створити Workout і WorkoutExercise одним транзакційним запитом. include повертає повні об'єкти вправ для відображення на frontend.

### Отримання списку тренувань з пагінацією

Для списку тренувань використовується Promise.all, щоб паралельно виконати findMany і count. Це швидше, ніж два послідовні запити.

```typescript
export const getUserWorkouts = async (req: AuthRequest, res: Response) => {
  const userId = req.userId!;
  const { startDate, endDate, limit = '20', offset = '0' } = req.query;
  const where: any = { userId };
  if (startDate) where.date = { ...where.date, gte: new Date(startDate as string) };
  if (endDate) where.date = { ...where.date, lte: new Date(endDate as string) };

  const [workouts, total] = await Promise.all([
    prisma.workout.findMany({
      where, take: parseInt(limit as string), skip: parseInt(offset as string),
      orderBy: { date: 'desc' },
      include: { exercises: { include: { exercise: true }, orderBy: { order: 'asc' } } }
    }),
    prisma.workout.count({ where })
  ]);
  res.json({ workouts, total });
};
```

**Пояснення:** total потрібен для пагінації на frontend. Promise.all виконує обидва запити одночасно, що скорочує час відповіді.

### Статистика тренувань: агрегація, серія, досягнення

getWorkoutStats рахує загальну кількість тренувань, середню тривалість, середню оцінку, кількість за тиждень і місяць, порівняння з попереднім періодом, серію днів підряд і досягнення.

```typescript
// Агрегація за період
const stats = await prisma.workout.aggregate({
  where: {
    userId,
    date: { gte: startDate }
  },
  _count: { id: true },
  _avg: { duration: true, rating: true }
});

// Розрахунок серії (consecutive days)
const sortedDates = recentWorkouts.map(w => w.date.toISOString().split('T')[0]).sort().reverse();
let streak = 0;
let currentDate = new Date();
currentDate.setHours(0, 0, 0, 0);

for (let i = 0; i < 30; i++) {
  const dateKey = currentDate.toISOString().split('T')[0];
  if (sortedDates.includes(dateKey)) {
    streak++;
    currentDate.setDate(currentDate.getDate() - 1);
  } else {
    break;
  }
}

// Досягнення (achievements)
const achievements = await calculateAchievements(userId, stats._count.id, streak, recentWorkouts.length);
```

**Пояснення:** Серія рахується від сьогодні назад: скільки днів підряд є тренування. Досягнення (First Steps, Week Warrior, Century Club тощо) визначаються умовами на основі totalWorkouts, streak і recentCount.

## Етап 7. Реалізація API-клієнта на frontend

На frontend формується єдиний шар запитів: базовий URL, заголовки з токеном, обробка помилок, автоматичний редірект на /login при 401.

### Єдина точка для API та токен

Всі методи звертаються до одного API_URL. Токен береться з localStorage і додається до кожного захищеного запиту.

```typescript
// frontend/app/lib/api.ts
const API_BASE = process.env.NEXT_PUBLIC_API_URL || 'http://localhost:5000';
const API_URL = API_BASE.endsWith('/api') ? API_BASE : `${API_BASE.replace(/\/$/, '')}/api`;

function clearAuthAndRedirect() {
  if (typeof window !== 'undefined') {
    localStorage.removeItem('token');
    localStorage.removeItem('user');
    window.location.href = '/login';
  }
}

async function handleResponse<T>(res: Response): Promise<T> {
  if (!res.ok) {
    if (res.status === 401) {
      clearAuthAndRedirect();
    }
    const error: ApiError = await res.json().catch(() => ({ error: 'Network error' }));
    const msg = error.message || error.error || `HTTP error! status: ${res.status}`;
    throw new Error(msg);
  }
  return res.json();
}
```

**Пояснення:** При 401 (невалідний або відсутній токен) handleResponse очищає localStorage і редіректить на /login. Це гарантує, що користувач не залишиться на захищеній сторінці з простроченим токеном.

### Приклад захищеного запиту з токеном

Кожен метод для захищених ендпоінтів додає заголовок Authorization. Без нього backend поверне 401, і користувач буде вилогінений.

```typescript
getWorkouts: async (filters?: Record<string, string>) => {
  const token = localStorage.getItem('token');
  const params = new URLSearchParams(filters);
  const res = await fetch(`${API_URL}/workouts?${params}`, {
    headers: {
      'Authorization': `Bearer ${token}`
    }
  });
  return handleResponse(res);
},

getWorkoutStats: async (days?: number): Promise<WorkoutStats> => {
  const token = localStorage.getItem('token');
  const url = days ? `${API_URL}/workouts/stats?days=${days}` : `${API_URL}/workouts/stats`;
  const res = await fetch(url, {
    headers: {
      'Authorization': `Bearer ${token}`
    }
  });
  return handleResponse<WorkoutStats>(res);
},
```

**Пояснення:** Раніше частина методів (getWorkoutStats, getGoals, getRecommendations) не передавала токен. Після успішного логіну dashboard викликав ці методи, отримував 401 і редіректив на login. Додавання Authorization до всіх захищених запитів вирішило проблему.

### Логін через API-клієнт

Логін не потребує токена — він його отримує. Після успішної відповіді токен і user зберігаються в localStorage, виконується редірект на dashboard.

```typescript
login: async (email: string, password: string): Promise<{ user: ProfileData; token: string }> => {
  const url = `${API_URL}/auth/login`;
  const res = await fetch(url, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ email, password })
  });
  const data = await res.json().catch(() => ({}));
  if (!res.ok) {
    const code = data.code || '';
    const msg = data.message || data.error || (res.status === 401 ? 'Невірний email або пароль' : 'Помилка входу');
    const err = new Error(code ? `${msg} [${code}]` : msg) as Error & { status?: number; code?: string };
    err.status = res.status;
    err.code = code;
    throw err;
  }
  return data;
},
```

**Пояснення:** На frontend email передається вже нормалізований (trim + toLowerCase), щоб узгодити з backend. Код помилки (USER_NOT_FOUND, BAD_PASSWORD) дозволяє показувати більш точні повідомлення.

## Етап 12. Експорт даних та тестування

На фінальному етапі реалізовано експорт тренувань і харчування в Excel та PDF. Додано логування, документацію, підготовку до захисту.

### Експорт тренувань у Excel

Користувач може експортувати тренування за діапазоном дат. ExcelJS формує workbook з заголовками, даними та стилізацією.

```typescript
// backend/src/controllers/export.controller.ts (фрагмент)
import ExcelJS from 'exceljs';

export const exportWorkoutsExcel = async (req: AuthRequest, res: Response) => {
  const userId = req.userId!;
  const where: Record<string, unknown> = { userId };
  const dateFilter = buildDateRangeFilter(req.query.startDate, req.query.endDate);
  if (dateFilter) where.date = dateFilter;
  const workouts = await prisma.workout.findMany({
    where,
    include: { exercises: { include: { exercise: true } } },
    orderBy: { date: 'desc' }
  });

  const workbook = new ExcelJS.Workbook();
  const ws = workbook.addWorksheet('Тренування');
  ws.columns = [
    { header: 'Дата', key: 'date', width: 15 },
    { header: 'Тип', key: 'type', width: 15 },
    { header: 'Тривалість (хв)', key: 'duration', width: 15 },
    { header: 'Оцінка', key: 'rating', width: 10 },
    { header: 'Вправи', key: 'exercisesCount', width: 10 },
    { header: 'Нотатки', key: 'notes', width: 30 }
  ];

  workouts.forEach(w => ws.addRow({
    date: new Date(w.date).toLocaleDateString('uk-UA'),
    type: w.type || '-',
    duration: w.duration || '-',
    rating: w.rating || '-',
    exercisesCount: w.exercises.length,
    notes: w.notes || '-'
  }));

  const buffer = await workbook.xlsx.writeBuffer();
  res.setHeader('Content-Type', 'application/vnd.openxmlformats-officedocument.spreadsheetml.sheet');
  res.setHeader('Content-Disposition', `attachment; filename=workouts_${formatDate(new Date())}.xlsx`);
  res.send(buffer);
};
```

**Пояснення:** buildDateRangeFilter і applyWorkoutFilters формують where з query-параметрів. Файл генерується в пам'яті (writeBuffer) і відправляється через res.send. Content-Disposition з filename змушує браузер запропонувати збереження.

### Завантаження експорту на frontend

API-клієнт викликає ендпоінт експорту з токеном, отримує blob і створює тимчасове посилання для завантаження.

```typescript
// frontend/app/lib/api.ts
downloadExport: async (path: string, filename: string): Promise<void> => {
  const token = localStorage.getItem('token');
  const res = await fetch(`${API_URL}/export/${path}`, {
    headers: { 'Authorization': `Bearer ${token}` }
  });
  if (!res.ok) {
    const error: ApiError = await res.json().catch(() => ({ error: 'Network error' }));
    throw new Error(error.message || error.error || 'Помилка завантаження');
  }
  const blob = await res.blob();
  const url = window.URL.createObjectURL(blob);
  const link = document.createElement('a');
  link.href = url;
  link.download = filename;
  link.click();
  window.URL.revokeObjectURL(url);
}
```

**Пояснення:** createObjectURL створює blob URL для файлу. Програмний click на невидимому <a download> ініціює завантаження. revokeObjectURL звільняє пам'ять після кліку.

## Підсумок етапів розробки

1. **Підготовка** — конфігурація .env, скрипти, точка входу, graceful shutdown
2. **Архітектура** — роутери за доменами, health-check, rate-limit, CORS, error handler
3. **База даних** — Prisma schema (User, Workout, NutritionLog, Goal, Reminder, Recommendation, довідники), індекси, каскадне видалення
4. **Backend-каркас** — helmet, rate-limit для auth, централізована обробка помилок
5. **Авторизація** — bcrypt, JWT, authenticateToken, Zod-валідація, нормалізація email, auto-створення demo-користувача
6. **Бізнес-функціонал** — CRUD тренувань/харчування/цілей/нагадувань/рекомендацій, статистика тренувань, серія, досягнення
7. **API-клієнт** — єдиний шар fetch з токеном, handleResponse, clearAuthAndRedirect при 401
8. **Сторінки** — login, register, dashboard, workouts, nutrition, goals, reminders, profile, calculators, recommendations
9. **Дизайн** — темна тема, золоті акценти, дизайн-токени, картки, кнопки, навігація
10. **Контраст** — висококонтрастний текст, focus-visible
11. **Демо-дані** — seed-user, seed-demo (тренування, харчування, цілі, нагадування, рекомендації, шаблони)
12. **Експорт і підтримка** — Excel/PDF, логування, документація

Система розроблена поетапно: спочатку базовий функціонал, потім розширення та покращення. Код структурований з використанням модулів, валідації та централізованої обробки помилок для зручності підтримки.
